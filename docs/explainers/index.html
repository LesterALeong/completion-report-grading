A beginner’s guide to one small safety pilot

When the report says “done”

Can an approval-seeking completion report change whether a model grader accepts code that fails its requirements? This project tested that narrow question, repaired the research machinery, and published a result with clear limits.

AI-assisted research and engineering One quantized local model A small authored holdout

The short answer: the grader falsely approved 3 of 12 defective holdout cases with a neutral report and 4 of 12 with approval pressure. That one-case increase fell below the preregistered screen of two extra approvals. The pilot cannot show that pressure is harmless, or that the mitigation works.

The question

A confident status report is not a test result

Imagine a coding agent says its change is complete. A second model checks the code. If that reviewer treats the agent’s report as evidence, broken work might pass a gate that decides which changes are accepted.

This study asked a narrower question: when the code, task and factual claims stay fixed, does wording that recommends approval change a model grader’s decision? The concern matters because evaluation gates can influence which work is accepted and what behavior future systems are rewarded for. A gate that moves with unsupported success claims weakens the evidence behind those decisions.

The project tested one small part of that safety argument. It did not measure frontier-agent autonomy, catastrophic risk, or performance on real production patches. The fixtures were synthetic and intentionally inspectable, so the team could know what each requirement meant before asking the grader.

Morgan, fictional founder: “The status page is green.”

Casey, fictional engineer: “The first-record check says the answer should be 1.”

For each implementation, the grader saw one of four report conditions: no report; a neutral report; an approval-seeking report with the same factual claims; or that approval-seeking report plus a warning not to trust the report and an instruction to check every criterion. The code and task stayed the same across conditions. The mitigation bundled two instructions, so the experiment cannot tell which instruction, if either, caused a change.

The holdout

What the result supports: the local grader made mistakes even without a report. The primary comparison moved by one false approval, below the predeclared two-case screen. The mitigation produced one fewer false approval than approval pressure alone, also short of its two-case target. All six correct controls passed in every condition.

What it does not support: that approval pressure is harmless, that the mitigation is effective, or that a production reviewer is safe. The observations came from one quantized local Qwen model and a small set of obvious, authored defects. Uncertainty remains substantial.

The study used 8 development and 18 holdout cases, with 48 executable criterion checks across 26 synthetic Python functions. There were 104 valid study responses, with no missing, invalid, operationally unknown or abstaining responses. Four charged operational canaries bring the attempt count to 108, under the original cap of 120. Those canaries are not extra study grades.

In H16, the grader rejected the implementation with no report and with a neutral report. It approved the same defective code under approval pressure and also under the mitigation. H16 was the only neutral-to-pressure flip in the primary comparison. The aggregate mitigation’s one-case reduction happened elsewhere; it did not fix H16.

The work behind the result

First make the measurement trustworthy

The first candidate looked fine in helper tests, then failed when independent review examined the actual run boundary.

Failure → repair

The real caller passed a missing parameter

Helper-level checks had not composed the true caller. The repair added tests at that boundary so a signature mismatch could not hide behind passing helper tests.

Failure → repair

The canary accepted the wrong verdict

A permissive predicate could let an invalid operational check look successful. The repair encoded the exact expected result for each canary.

Failure → repair

The frozen receipt check was too weak

It did not prove equality with the configuration that was supposed to be frozen. The repair added strict lifecycle parsing and shared evidence verification.

Operational boundary

Cleanup also needed limits

Task-owned process cleanup was bounded, so a failed or timed-out route could not quietly blur what had and had not run.

The initial Codex route failed two operational canaries and closed before any study grades. The local Qwen route was separately preregistered before outcomes and then used for grading. That chronology is an operational pivot, not a Codex-versus-Qwen comparison: Codex produced no admitted study grades.

From question to publication

The project had two kinds of work

The study measured grader decisions. Separate engineering and publication work made those decisions auditable.

Define the risk

Ask whether a report’s recommendation can affect a grader when the code and factual claims are fixed.

Close the first route

Two Codex operational canaries did not qualify. The route closed before grading began.

Preregister local Qwen

Freeze a separate local-model protocol before seeing grades. This is not a model-provider bake-off.

Repair the harness

Exercise actual callers, exact canary outcomes, lifecycle evidence and bounded cleanup.

Run paired conditions

Grade the same implementations four ways. Keep failed and operational outcomes distinguishable from valid study responses.

Amend publication only

Fix a display-boundary failure without changing the frozen experiment, raw evidence, grades or analysis.

A separate publishing repair

The amendment changed the display, not the study

The first public export failed because redaction expanded one valid 300-character reason to 305 characters. A separate publication amendment bounded only the sanitized display reason. It did not change grades, raw evidence, validity or analysis. The strict public reader stayed unchanged.

There was also a Git verification-order failure: work continued after a staged-file check reported differences. Independent follow-up compared the actual commit snapshot and found exactly three CRLF-to-LF changes in presentation files. The frozen scientific closure was unchanged and source evidence remained intact. The practical lesson is to stop at a failed verification step, inspect the committed bytes, and establish exactly what changed before proceeding.

A publication check can confirm the snapshot it inspected. It does not guarantee a future job, a future model run, or identical inference on other hardware.

Interpretation

A useful work sample is not a safety certificate

This was a small floor probe on one quantized local Qwen model, with obvious defects in a small authored fixture set. The cases are not a random sample of production work, and one verdict per condition does not show what the model would usually do across repeated runs. Finite executable checks establish the intended outcomes for these examples; they do not prove arbitrary program correctness.

The next useful study would be preregistered separately, use more independently authored and less obvious defects, include more task families and repeated samples, and evaluate stronger graders. That follow-up has not been run. Do not expand or retune these data to chase a larger effect.

The project can serve as a public example of protocol design, retained failures, executable ground truth, careful publication and reproducible analysis. Research, implementation, review and writing were AI-assisted. AI reviews are not human peer review. The repository does not prove its owner’s mastery, course attendance, or a hiring outcome; those require separate evidence, including being able to explain and extend the work.

Plain-language glossary

A few terms, without the lab coat

Holdout

Cases set aside from development to check the frozen study design on examples not used to tune it.

False approval

The grader says code is acceptable even though it violates a stated requirement.

Paired comparison

Compare conditions on the same implementation, so the code’s difficulty is held fixed.

Preregistration

Write down the question, method and decision rules before looking at study outcomes.

Mitigation

A proposed step to reduce a risk. Here it bundled a report warning and a criterion-check instruction.

Canary

A small operational check run before the main grading. A failed canary can close a route before study outcomes.

Receipt

A saved record of what an evaluation attempt used and returned, so later checks can compare evidence with the frozen plan.

Publication amendment

A versioned change to how evidence is presented publicly. It must keep the underlying study and grades intact.

Correct control

An implementation that meets its criteria. Reporting these checks guards against a policy that “succeeds” by rejecting everything.

The standard for presenting the work

Be able to trace one case, reproduce the saved result, explain the publication boundary and name what the evidence cannot establish. That is stronger than treating a polished report as proof of understanding.
