# Code Mode host capability audit

**Decision: insufficient evidence to admit host enablement now.** Enabling an executor is not inherently equivalent to enabling a filesystem/browser/MCP tool. It is also not evidence that those capabilities remain absent. One bounded model-free capability inspection can resolve this only if existing installed interfaces expose the actual runtime registry and invocation contract; do not build another harness or spend another canary merely to discover the host's capabilities.

## What would be enough, without claiming OS isolation

Use at most one short existing-interface inspection, bounded to ten minutes and no model calls. Root may run exact host `--help` under the existing native Job, hash/retain the bounded output and confirm cleanup; help alone is not the capability proof. If supported installed CLI/debug interfaces or exact-version first-party implementation evidence expose the following facts, retain a small receipt and have them independently reviewed:

1. **Effective model-facing capability set for the exact proposed per-call argv.** Show which direct and nested namespaces are registered, not only feature booleans or a generic bundled-model list. Establish that shell/filesystem/web/apps/browser/computer/MCP/other workspace readers are absent or effectively excluded. If arbitrary JavaScript execution is available, establish its actual intrinsic imports/globals and whether those provide content access independently of registered tools. Do not assume that disabling named tools disables intrinsic host IO.
2. **Invocation and event boundary.** Establish that the host does not autonomously fetch private/context content during initialization and that any model-requested executor invocation is observable in the captured producer stream before its result is consumed. Show the actual envelope/type path for executor and nested calls. Existing parser rejection of unknown/tool items must catch that path; no success allowlist should be added for the executor. A self-report that no tool was used is insufficient.
3. **Same audited context/custody contract.** The exact host identity/configuration joins the admitted source/config fingerprint; host descendants remain inside the Job. Existing inherited-context controls, subscription environment filter, serialized inputs, fresh cwd, no retry and bounded private capture rules remain enforced. No global user config or security-control changes.

These are logical interface checks, not an escape-resistance or host OS isolation proof. Do not require or claim full sandbox certification. Conversely, an unavailable registry/event contract cannot be replaced with a successful final answer or a feature-list result.

## Accepted grades with zero tool events

Executor availability alone does not logically invalidate an accepted verdict. A grade can remain valid under audited logical isolation if the exact admitted context is label-free, content-access capabilities are excluded, the complete producer stream provides the reviewed invocation boundary, and no executor/content-tool invocation occurred. Merely enabling a host process is not a model tool call. Any observed executor invocation remains invalid even if its code only does arithmetic; it is outside this no-tool study. A marker refusal alone cannot prove an exhaustive capability or event boundary.

The currently retained evidence proves neither the complete effective capability set nor invocation-event completeness with the host enabled. Therefore this audit does not authorize a host-enabled canary. Nested disablement's two observed bootstrap failures also do not prove that enabling the host would preserve or violate logical isolation.
